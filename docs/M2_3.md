# M2.3 — Observation logbook and schedule linkage

M2.3 completes the first monitoring workflow: expected transmissions can now be connected to what was actually heard.

## Scope

- full observation logbook in the web UI
- create, edit and delete observations
- newest-first observation API output
- optional `schedule_id` on observations
- schedule/station integrity validation
- linked schedules cannot be deleted while observations reference them
- schedule station cannot be changed incompatibly with linked observations
- `Log heard` pivot from schedule archive and on-now/next dashboard
- prefill station, frequency and mode from the selected schedule
- client-side observation search across station, frequency, UTC time, mode, signal, transcription, notes and linked schedule

## API

- `GET /api/observations`
- `POST /api/observations`
- `PUT /api/observations/{id}`
- `DELETE /api/observations/{id}`

Existing station, schedule and now/next APIs remain supported.

## Integrity rules

An observation must reference an existing station. When `schedule_id` is set, the schedule must exist and belong to the same station. A schedule referenced by observations cannot be deleted until those observations are deleted or unlinked.
