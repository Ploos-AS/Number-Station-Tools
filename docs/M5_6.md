# M5.6 — restore receipt integrity / hash chain

M5.6 makes the persistent restore receipts introduced in M5.5 tamper-evident.

## Receipt chain

Each restore receipt now stores:

- `previous_hash` — SHA-256 hash of the preceding receipt, blank for the first receipt
- `receipt_hash` — SHA-256 of the receipt's canonical JSON content with `receipt_hash` blanked

Receipts remain in append order in the local receipt store. The current chain head is the `receipt_hash` of the newest appended receipt.

Before a new receipt is appended, the complete existing chain is verified. A broken chain is not extended.

This is tamper evidence, not an external signature or trusted timestamp. An attacker that can rewrite the complete local receipt file and recompute every hash can create a new internally consistent chain. External anchoring is outside M5.6 scope.

## Verification API

`GET /api/recording-archive/receipts/verify`

A valid response reports:

- `valid: true`
- receipt `count`
- current `head_hash`

A failed verification reports `valid: false` and identifies the first failing receipt/index plus a reason such as:

- `previous_hash` does not match the preceding receipt
- missing/invalid receipt hash
- non-hexadecimal receipt hash
- receipt content hash mismatch

The endpoint is read-only.

## Legacy M5.5 migration

An M5.5 receipt file contains no hash fields. If an existing file has receipts and every receipt is completely unchained, M5.6 seals the receipts in their existing append order and atomically persists the new chain when the store is opened.

That migration establishes tamper evidence from the M5.6 migration point onward. It cannot prove that the legacy M5.5 data had not been modified before migration.

Mixed partially-hashed data is not treated as legacy. Verification will report it as invalid, and new receipt appends will be refused.

## Persistence and failure semantics

The receipt store remains a separate local JSON file beside the recording store and is saved atomically with mode `0600`.

A successful restore whose receipt cannot be persisted is still reported as a restore whose audit persistence failed, matching M5.5 semantics. M5.6 additionally refuses to append a receipt when the existing chain fails integrity verification.

No archive payload, audio content or derived signal data is duplicated into the receipt log.

## Scope exclusions

M5.6 does not provide:

- digital signatures or public-key verification
- external timestamping
- remote transparency logs
- immutable/WORM storage
- external chain-head anchoring
- UI visualization of the receipt history

Those can be layered on later without changing the restore archive format.
