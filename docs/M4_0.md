# M4.0 — Signal workbench / recording playback

M4.0 turns the managed recording archive into an interactive local signal workbench.

## Scope

- managed recordings get an inline streaming endpoint at `GET /api/recordings/{id}/stream`
- the existing attachment download endpoint remains unchanged
- streaming remains confined to server-managed files under the configured audio directory
- HTTP byte ranges are supported for browser seeking without loading the entire recording first
- the recording archive injects native browser audio controls for managed recordings
- current playback time and duration are shown beside the player
- playback position is mirrored as a cursor across waveform and mini-spectrogram previews
- preview byte arrays stored by Go as base64 JSON strings are decoded in the browser before rendering
- external metadata-only recordings do not receive a player

## Local-first behavior

No audio is uploaded to an external provider. Playback reads the same managed file already stored under `/data/audio` (or `NUMBER_STATION_TOOLS_AUDIO_DIR`). No API key, AI service, transcoder, or remote media service is involved.

Browser codec support determines whether a particular WAV/FLAC file can be played natively. The server does not transcode audio in M4.0.

## Safety

The stream endpoint reuses the managed-recording path containment rule: only the basename of the server-generated managed path is resolved inside the configured audio directory. External metadata paths cannot be streamed.

## Qualification

The managed-audio integration test now verifies:

- normal attachment download still works
- inline streaming returns the original audio bytes
- the response uses inline content disposition
- byte ranges are advertised
- a `Range: bytes=0-3` request returns HTTP 206 and the WAV `RIFF` prefix

The standard CI gate remains formatting, tests, vet, Go build, and container build.
