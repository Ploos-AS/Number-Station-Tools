# M5.8 — Local restore-anchor registry

M5.8 adds local operational history around the M5.7 external receipt-chain anchor.

## Scope

- Every successful `GET /api/recording-archive/receipts/anchor` request records metadata for the exported anchor in a separate local registry.
- The registry stores only an ID, UTC export time, receipt count and head hash. It does not store archive/audio payloads.
- `GET /api/recording-archive/receipts/anchors?limit=50` returns newest registered exports first. Limit must be 1–200.
- `GET /api/recording-archive/receipts/anchors/status` compares the latest registered anchor with the current verified receipt chain.
- Status is `never-anchored`, `current`, `extended`, or `mismatch`.
- `receipts_since_last_anchor` reports chain growth since the latest registered anchor.
- Registry persistence is a separate atomic JSON file next to recording data with mode `0600`.

## Trust boundary

The registry is operational metadata, not an independent trust anchor. A local attacker able to rewrite the appliance data can also rewrite this registry. M5.7 security still depends on retaining the downloaded anchor outside the appliance trust boundary. M5.8 only makes it easier to see when an anchor was requested/exported and how far the local receipt chain has grown since then.

An HTTP export being registered means the server accepted and generated the export response; it cannot prove that the client safely retained the downloaded file.
