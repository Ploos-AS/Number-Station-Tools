# M5.2 — Portable archive restore planning

M5.2 adds a dry-run planning step before M5.1 archive restore.

## API

`POST /api/recording-archive/plan`

The request body is the same M5.0 `tar.gz` archive accepted by the restore endpoint. The planner applies the same archive structure, manifest-version, managed-path, size, SHA-256, audio-signature, metadata and annotation validation used by restore, then classifies each recording without committing it.

Each result entry is classified as:

- `import` — the recording can be added safely
- `duplicate` — an equivalent recording already exists
- `conflict` — the recording ID or managed-audio destination collides with different local state
- `unmatched` — the referenced observation does not exist locally

The plan also reports how many annotations would be imported or skipped as duplicates for each non-conflicting recording.

## Safety

Planning never appends recording metadata, saves annotations, moves a staged audio file into its final location, overwrites managed audio, or changes existing recording state. Archive parsing uses temporary staging only so the same local audio validation and preview reconstruction code can be exercised; that staging directory is removed before the request completes.

The actual restore endpoint remains `POST /api/recording-archive/import` and keeps the M5.1 conservative collision and rollback behavior.

## UI

The Portable recording archive panel now offers **Plan restore** beside the restore action. Planning shows per-recording action, reason and annotation import/skip counts before the operator chooses whether to perform the actual restore.
