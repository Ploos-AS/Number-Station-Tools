# M5.3 — Restore selection and policy

M5.3 adds an operator-controlled selective restore path on top of the M5.2 dry-run plan.

## API

`POST /api/recording-archive/import-selected?recording_id=<id>&recording_id=<id>`

The request body is the same M5.0 `tar.gz` archive used by planning and full restore.

## Policy

Selective restore is intentionally strict:

- at least one recording ID must be selected;
- selected IDs must exist in the archive;
- the full archive structure and managed payload integrity are still validated;
- selected recordings must reference observations that already exist locally;
- a selected recording that is already present as an equivalent duplicate is rejected;
- a selected recording whose ID conflicts with different local metadata is rejected;
- an existing managed-audio destination is a conflict and is never overwritten;
- unselected archive entries are skipped by policy and are not persisted;
- selected annotations are validated, receive new local IDs, and duplicate annotations are suppressed;
- filesystem moves are rolled back if metadata persistence fails.

There is no force-overwrite mode in M5.3.

## UI

After **Plan restore**, entries classified as `import` receive checked selection boxes. `duplicate`, `conflict`, and `unmatched` entries remain informational and cannot be selected. **Restore selected** sends only the checked import candidates to the strict selection endpoint.

The existing full safe restore remains available for backward compatibility.

## Local-first scope

All validation, planning, selection and restore processing remains local. No API key, cloud service, AI provider or external receiver integration is required.
