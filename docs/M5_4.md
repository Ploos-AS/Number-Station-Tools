# M5.4 — Restore plan token

M5.4 binds selective archive restore to the exact dry-run plan the operator reviewed.

`POST /api/recording-archive/plan` now returns a deterministic SHA-256 `plan_token`. The token covers the validated portable manifest, managed-audio inventory (path, size and SHA-256), the complete restore plan and a canonical snapshot of local recordings, annotations and observations.

Selective restore requires that token:

`POST /api/recording-archive/import-selected?recording_id=...&plan_token=...`

Before any selected restore is committed, the archive is staged and validated again, the current plan is recomputed, and its token must match the operator-approved token. A changed archive, recording set, annotation set or observation set causes the request to fail with a re-plan-required error. Selected entries must still be `import` candidates; conflicts, duplicates, unmatched entries and unknown IDs remain non-overridable.

The browser UI stores the token only in memory after a successful plan response, sends it with selective restore, and clears it when the archive selection changes, restore completes, or an error invalidates the plan.

The existing full safe restore endpoint remains available and unchanged. M5.4 specifically hardens the `plan -> selective restore` workflow against stale decisions.
