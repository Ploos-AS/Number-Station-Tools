# M5.7 — External restore receipt chain anchors

M5.7 extends the M5.6 tamper-evident restore receipt chain with a small,
deterministic anchor that can be copied outside the appliance trust boundary.

## Anchor format

`GET /api/recording-archive/receipts/anchor` returns and downloads JSON:

```json
{
  "version": 1,
  "receipt_count": 42,
  "head_hash": "0123456789abcdef..."
}
```

The anchor contains no receipt contents, archive payloads, recording metadata or
audio. The file is deterministic for a given receipt-chain state: it contains only
the schema version, number of receipts covered and SHA-256 chain head.

For an empty receipt chain, `receipt_count` is `0` and `head_hash` is omitted.

## Verification

`POST /api/recording-archive/receipts/anchor/verify` accepts one anchor JSON object.
The request body is limited to 64 KiB, unknown JSON fields are rejected, and trailing
JSON values are rejected.

Verification first validates the complete local M5.6 receipt chain. It then checks:

- anchor schema version is supported
- `receipt_count` is not negative
- a non-empty anchor has a 64-character hexadecimal `head_hash`
- the anchor does not refer to more receipts than exist locally
- the stored anchor hash equals the receipt hash at exactly `receipt_count - 1`

A valid result has status:

- `match` — the anchor covers the current complete chain
- `extended` — the anchored prefix is still intact and newer receipts have been
  appended locally since the anchor was exported

A mismatch returns HTTP 409 with a structured result containing `valid: false`.
Malformed JSON returns HTTP 400.

## Why prefix verification matters

An anchor is expected to become older as new restores occur. Requiring its hash to
match the current head would make every old anchor obsolete after one new receipt.
M5.7 instead verifies the exact historical chain position identified by
`receipt_count`. This lets an offline anchor remain useful while the local audit log
continues to grow.

## Operational use

For stronger evidence than local hash chaining alone, export anchors periodically
and retain copies outside the appliance, for example on:

- another machine
- offline/removable storage
- a backup system with separate credentials
- a Git repository or other independently administered store

The appliance itself does not contact any external provider and does not require an
API key.

## Security boundary

M5.7 detects rewriting of a locally anchored receipt-chain prefix when a trusted
independent copy of the old anchor remains available. It is not a digital signature,
trusted timestamp, transparency log or third-party attestation. An attacker who can
rewrite both the local receipt chain and every independent anchor copy can still
replace the evidence.

## API

- `GET /api/recording-archive/receipts/anchor`
- `POST /api/recording-archive/receipts/anchor/verify`

M5.7 does not change archive export, restore planning, selective restore, recording
storage or audio handling.
